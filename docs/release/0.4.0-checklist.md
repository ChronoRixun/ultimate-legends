# Launcher 0.4.0 release checklist (stable, with the Beta update channel)

**Plan (owner, 2026-10-22):** launcher 0.4.0 ships as a normal **stable** release with the Online section **and** the
Beta update channel (draft PR #14). XML2 Fix 1.8.0 and Legends Classic 0.3.0 come out **as betas first**
(pre-releases `v1.8.0-beta.1` / `v0.3.0-beta.1`, never "latest"). For a while, Stable players have launcher 0.4.0
with XML2 Fix 1.7.1 and builder 0.2.5: their Online section says online play arrives with Legends Classic 0.3.0 and
opens Settings → Update channel; **online play needs the Beta channel until Legends Classic 0.3.0 is final**.

The runbook and evidence record for the coordinated release. Fill in every field and every result slot against the
**exact candidate commit**; a slot stays **NOT RUN** until there is real evidence (a CI run link, a log, a screenshot,
a tester's note). Unit and UI tests passing do not make the release ready: sections C to G need people, devices and
the production services.

Results: **PASS**, **FAIL** (with a link to the issue), or **NOT RUN**.

## H. Release mechanics (owner)

Recommended order:

0.4.0 ships from `integration/0.4.0` (PR #11 + PR #12 combined; its draft PR to `main` supersedes both).

1. **Pin the candidate first:** on `integration/0.4.0`, commit the final `CHANGELOG.md` heading
   (`## 0.4.0 - <release date>`) and the final `docs/release/v0.4.0-notes.md` (the player guide's link, if it is
   published by then). That commit's SHA is the candidate: write it in the table at the top.
2. Run A1-A4 on that SHA (the draft PR's Build run), then B, then C-E and I with a package built from it and the
   production broker.
3. Before or in the release window: publish and verify the betas `v1.8.0-beta.<n>` and `v0.3.0-beta.<n>` as
   pre-releases (F1, F2, F2b; "How to cut a beta" below). The stable 0.2.5 / 1.7.1 stay latest.
4. Merge the PR so that `main` is the candidate SHA itself (a merge that makes a new commit makes a new SHA: then
   rerun A1-A4 on it, or tag the verified SHA directly). Tag **the verified SHA** `v0.4.0` and push the tag: the
   workflow builds, tests, packages and publishes the release with `docs/release/v0.4.0-notes.md`. Then F3 and G.

Any commit after step 1 - a date fix, a typo in the notes - makes a new SHA: it is a new candidate, and A-E (or at
least A, B1 and the C checks its change touches, recorded here) run again on it before the tag. The player guide is
not published yet: link it from the release notes (and, in a later launcher, from How online works) only once its
real URL exists.

## How to cut a beta

The same steps for every repository that the update channel follows. A beta is a GitHub **pre-release** that is
**never "latest"**, with **the same asset names** as a stable release; Beta launchers take the highest version
(SemVer: `1.8.0-beta.1` < `1.8.0-beta.2` < `1.8.0`), Stable never sees it.

**Launcher (this repository)**
1. On the branch to test, write `docs/release/v<base>-notes.md` (for `v0.4.1-beta.1`: `v0.4.1-notes.md`) if the
   release should have notes; the workflow puts a "Beta - test build" banner above them (else the generic line).
2. Tag the commit `v<major>.<minor>.<patch>-beta.<n>` (or `-rc.<n>`, lower case) and push the tag. Nothing else: the
   Build workflow (`tools/release_tag.py`) packages `ultimate-legends-<version>-win64-portable.zip` with the suffix in
   `<version>` plus `SHA256SUMS.txt`, and `tools/publish_release.py` runs `gh release create … --prerelease
   --latest=false`, then fails the job unless `releases/tags/<tag>` says `"prerelease": true` with both files and
   `releases/latest` is still the release it was before. A re-run of the job uploads the files again with
   `--clobber` (never a new release). Any other suffix (`-alpha`, `-hotfix`) or upper case (`-Beta.1`) stops the run
   before packaging.
3. Check the release page says **Pre-release**, `releases/latest` still names the stable version, and a launcher on
   Beta is offered it (I5). The launcher built at the tag calls itself `<major>.<minor>.<patch>-beta.<n>` (its
   VERSIONINFO stays numeric).
4. The final release is a normal stable tag (`v0.4.1`): Beta launchers move to it on their own.

**XML2 Fix and Legends Classic** (their own pipelines)
1. Tag `v<version>-beta.<n>`; publish it as a pre-release, never latest.
2. Upload the same files as a stable release: `ultimate-legends.json` and every file it lists (XML2 Fix);
   `xml1-builder.json` and its zip (Legends Classic). A release still missing them is skipped by Beta until they
   are there.
3. Legends Classic: `xml1-builder.json`'s `version` is the tag's version (`0.3.0-beta.1`); its `requires_xml2fix`
   accepts the beta fix it is meant for: beta and rc tags write `>=1.8.0-0`, stable tags `>=1.8` (F2b).
4. The XML2 Fix DLL's version resource may stay numeric (`1.8.0.0`): the launcher records the tag's version for the
   file it installed.

## Beta rules

For every repository the update channel follows (this one, XML2 Fix, Legends Classic). They keep Beta testers'
installs consistent and Stable players away from betas.

1. **Never delete a published beta.** Testers have it installed and recorded (`clients\<game>-release.json`), and
   Beta's cached choice may name it. A bad beta is fixed forward: publish `-beta.<n+1>`, which every Beta launcher
   takes at its next check.
2. **Tag the beta pairs together.** An XML2 Fix beta and the Legends Classic beta built and tested with it are
   published together with the same number: fix `v1.8.0-beta.<n>` with builder `v0.3.0-beta.<n>`. Never publish one
   half of a pair that only works with the other.
3. **A fix beta that changes the online protocol** (what the broker or a room expects) **bumps the builder's
   requirement and the game version token**: the paired builder's `requires_xml2fix` names that beta
   (`>=1.8.0-beta.<n>`) and its `GameVersion` changes, so older builds are asked to rebuild (the Online section's
   "Rebuild to play online") and the room browser greys out rooms of other builds.
4. **The rc and the final come from the same tree.** Fast-forward the release branch to the last rc's commit and tag
   the final there: `git diff v<x.y.z>-rc.<n> v<x.y.z>` is empty. A change after the rc is a new rc.
5. **Never create releases by hand in the web UI.** Its form defaults to a full release and to "Set as the latest
   release": one click and every Stable launcher installs a beta. The tag's workflow is the only publisher (for the
   launcher, `tools/publish_release.py` refuses to change a release whose pre-release flag is wrong).
6. **After every publish, check `releases/latest` and the tag's `prerelease` flag** (the launcher's workflow fails
   itself; for the companions, by hand):
   `gh api repos/<owner>/<repo>/releases/latest --jq .tag_name` names the previous stable release, and
   `gh api repos/<owner>/<repo>/releases/tags/<tag> --jq '.prerelease, [.assets[].name]'` says `true` and lists
   every file.
7. **Tags are lower case** (`-beta.<n>`, `-rc.<n>`): the launcher and `tools/release_tag.py` refuse `-Beta.1`.
8. **Testers who used a hand-copied test kit** (a `dinput.dll` copied by hand, not installed by the launcher): until
   a launcher with the no-record repair (I9, this release) is on their PC, press **Uninstall**, then **Verify
   Files**, on that game, so the launcher installs the channel's fix and records it. A launcher before it treats
   the hand-copied 1.8.0 as newer than any `1.8.0-beta.<n>` and keeps it.
